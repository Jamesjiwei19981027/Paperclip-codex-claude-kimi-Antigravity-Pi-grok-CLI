# 成员本机 Codex 智能体接入 Paperclip 的可行性方案

日期：2026-10-25  
状态：只读代码研究，未改代码，未实测。标"未验证"的地方是假设，需要在专用服务器上验证。

## 要解决的问题

团队每个人的 Codex 智能体都受同一个 Paperclip 统一调度，和现在的使用方式一样：负责人派任务，智能体自动开工，做完自己把评论、报告、状态交回看板。

硬约束（来自你）：

1. 每个成员的 Codex 用自己的账号和额度，账号不能放服务器；
2. 智能体要操作成员本机环境（设备、模拟器、本地软件），所以必须在成员电脑上跑；
3. 大部分成员在局域网，少数通过 frp 访问；
4. 不同成员的 Codex 版本可能不同、会自动更新，不能依赖它。

## 代码研究结论

### 1. 「运行」只能由服务器创建，成员端不能自己建

- 路由里没有任何"智能体自己创建运行"的接口，只有唤醒（`POST /agents/:id/wakeup`）、取消、查询。
- 运行由服务器在唤醒智能体时创建，再调用适配器的 `execute()`；`execute()` 返回，这次运行就结束。
- 所以"成员端自己领任务、手上没有运行编号"这个问题，答案是：**不要让成员端自己建，而是让服务器端的适配器先建好运行，再把运行编号和令牌交给成员端。**

### 2. 适配器的 `execute()` 已经拿到了成员端需要的一切

`packages/adapter-utils/src/types.ts` 的 `AdapterExecutionContext` 里有：

- `runId`：这次运行编号；
- `authToken`：这次运行的短期令牌（本地 Codex 适配器就是把它放进 `PAPERCLIP_API_KEY` 环境变量）；
- `agent`、`config`、`context`：智能体和任务信息；
- `onLog`、`onMeta`、`onEvent`、`onUsage`：把日志和事件写回看板；
- `signal`：操作员点取消时触发；
- `onDispatch()`：告诉系统"已经派出去了"，没有本地进程的适配器就用它。

### 3. 先例：没有本地进程的适配器已经存在

- `http` 适配器和 `openclaw_gateway` 适配器都不在服务器上起进程，靠 `onDispatch()` 声明已派发。
- 但它们都是**服务器连到远端**（服务器发 HTTP 请求或主动开 WebSocket）。这个方向对 frp 成员不通，因为服务器无法主动连到他们的电脑。
- 运行回收逻辑（`heartbeat/recovery.ts`）靠进程号判断存活，主要针对本地进程；对无进程运行怎么判超时，**未验证**，需要读 `run-lifecycle.ts` 和 watchdog 部分。

### 4. 外部适配器插件机制存在

`server/src/adapters/plugin-loader.ts` 可以从插件目录加载外部适配器；`builtin-adapter-types.ts` 注明外部插件不能替换内置类型，但可以新增类型。所以新适配器可以不动核心适配器列表，作为插件或新增内置类型都行（选哪个**未验证**，取决于插件目录部署是否方便）。

### 5. `codex_local` 的远程路径不适合 Windows 成员

`adapter-utils/src/ssh.ts` 大量使用 `mkdir -p`、`mktemp`、`.bashrc`、`du -sk` 等 POSIX 命令。Windows 原生 OpenSSH 不能直接用。所以"服务器 SSH 进成员 Windows 电脑"这条路不推荐。

## 推荐方案：成员端主动长连接 + 服务器端「成员智能体」适配器

```text
成员电脑（局域网或 frp）                          Paperclip 服务器
┌──────────────────────────┐   出站 WebSocket    ┌─────────────────────────────┐
│ 本机代理（常驻、开机自启）  │ ───────────────────▶│ 新适配器 member_agent          │
│  ├ 固定版本 Codex（自带）   │                    │  execute() 被唤醒时：          │
│  ├ 该成员自己的 CODEX_HOME  │ ◀── 任务包 ─────── │   1. onDispatch()             │
│  └ 本机工作目录             │                    │   2. 把 runId、authToken、     │
│                           │ ── 日志/事件/结果 ─▶│      context 推给在线的代理     │
└──────────────────────────┘                    │   3. 等代理回报，转成 onLog/    │
                                                │      onEvent，最后返回结果      │
                                                └─────────────────────────────┘
```

流程：

1. 代理用该智能体的专属 Key 向服务器建立长连接，服务器据此知道该智能体**在线**。
2. 负责人派任务，服务器按现有机制唤醒智能体，创建运行，调用 `member_agent` 适配器的 `execute()`。
3. 适配器把运行编号、令牌、任务上下文推给在线代理，并立即调用 `onDispatch()`。
4. 代理在本机启动固定版本 Codex，设置 `PAPERCLIP_API_KEY=<令牌>`、`PAPERCLIP_RUN_ID=<运行编号>`、`PAPERCLIP_API_URL=<成员能访问的地址>`，其余行为和现在本地 Codex 一样：领任务、改状态、写评论、交报告，都带运行编号，审计链完整。
5. 代理把 Codex 的输出实时回传，适配器写进看板；结束时回传退出码和用量，适配器返回结果，运行正常结束。
6. 操作员点取消时，适配器的 `signal` 触发，通知代理终止本机进程。

为什么这样选：

- 只有出站连接，局域网和 frp 成员同一套；
- 运行由服务器创建，编号、令牌、审计、看板显示全部沿用现有机制，不需要改核心；
- 账号只在成员电脑上，额度算在各人头上；
- 代理自带并固定 Codex 版本，成员自己的桌面版随便更新。

### 代理里如何复用现有 Codex 适配器逻辑（关键，未验证）

最省事的做法是：代理直接把 `@paperclipai/adapter-codex-local` 当库使用，在本机用「本地」执行目标调用它的 `execute()`，这样提示词、技能注入、会话续接、日志格式都和现在完全一致，不用重写。

需要验证的点：

- `AdapterExecutionContext` 里有函数型字段（`onLog`、`getFreshSessionHandoff`、`onCancellationReady` 等），不能直接序列化，要在代理端用远程调用方式还原；
- 工作目录由服务器解析，成员端要有"项目 → 本机目录"的映射（每人本机代码位置不同）；
- 会话续接（`previous_response_id`、会话参数）保存位置要对：会话数据留在成员本机，服务器只存引用；
- 令牌有效期要覆盖一次运行的时长。

## 其他可选方案（不推荐）

| 方案 | 不推荐的原因 |
|---|---|
| 服务器 SSH 进成员电脑 | 远程路径按 POSIX 写，Windows 不通；frp 成员要穿透各自 SSH 端口 |
| 沿用 `http` / `openclaw_gateway` 样式（服务器连成员） | 方向错，frp 成员不可达 |
| 用 `process` 适配器 + 服务器侧中继脚本 | 每次运行占一个服务器进程，且要自己处理中继状态，比专用适配器更脆 |
| 智能体全放服务器 | 违反账号与本机环境两条硬约束 |

## 在专用服务器上的验证计划

按风险从高到低，每步有明确通过标准：

1. **适配器骨架**：新建 `member_agent` 适配器，`execute()` 只做"推任务、等一句回报、返回成功"。通过标准：看板上出现一次完整运行，状态正确，日志可见。
2. **无进程运行的超时与回收**：验证 `onDispatch()` 之后、代理长时间不回报时，系统如何判定；代理正常运行 30 分钟以上不被误回收。通过标准：正常长任务不被杀，异常能被标记失败并可重新唤醒。
3. **令牌与运行编号**：代理用推下来的令牌调用领任务、改状态、写评论、传文档。通过标准：所有写操作带运行编号，活动日志归属正确。
4. **接入 Codex**：代理调用 Codex 适配器逻辑，完成一个真实小任务（读文件、改文件、提交报告）。通过标准：产物经独立核对，用量和日志与本地适配器一致。
5. **取消**：操作员取消运行，本机 Codex 进程在限定时间内被终止。
6. **局域网 + frp 两种接入**：同一智能体分别从内网地址和 frp 域名连入，行为一致；WebSocket 在 frp 下稳定。
7. **版本固定**：代理按服务器下发的版本号自动切换自带的 Codex，成员本机桌面版更新不影响。
8. **两个成员并行**：两个成员同时有任务，互不影响，看板分别显示。

## 已知风险

- 无进程运行的回收与超时逻辑未读完，是最大不确定项；
- 函数型上下文字段的远程还原工作量，可能比预期大；
- 令牌有效期、会话续接在远端的行为未验证；
- 每个成员要装一次代理并登录一次 Codex，需要做安装包和使用说明；
- 本方案没有处理断网与关机（按你的要求暂不考虑），上线前要补"运行卡住如何人工清理"的操作办法。
